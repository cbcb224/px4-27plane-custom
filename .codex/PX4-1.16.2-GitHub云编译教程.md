## 1. 纯云端编译方案

PX4 的 NuttX 固件需要 Linux 工具链、CMake、Python 依赖、NuttX 配置工具和交叉编译器。本方案把这些工作全部交给 GitHub Actions，Windows 只负责编辑源码、Git 版本管理和烧录。

```text
Windows:
  编辑 boards/<vendor>/<model>/
  Git 提交并推送
        |
        v
GitHub Actions (ubuntu-latest):
  递归检出 PX4 和子模块
  在官方 NuttX Docker 镜像中执行 make
  校验目标并上传 .px4 / .elf / .bin
        |
        v
Windows:
  下载 artifact
  QGC 烧录应用程序
  SWD/JTAG 或 DFU 烧录首次 bootloader
```

这样做的优点：

- 不需要安装 WSL、Ubuntu、Docker Desktop、CMake 或 ARM 交叉编译器。
- 编译器版本、工具链和清理后的构建目录都由云端提供，减少本机环境差异。
- 每次构建都有 commit、目标、镜像 tag、run number 和构建时间记录。
- 本地只保留 PX4 源码、板卡代码和 Git 提交，不需要保留本地 `build/` 产物。
- 私有仓库可以隐藏源码，但会消耗 GitHub Actions 额度。

必须明确：**云编译只证明代码可以生成固件。** 它不检查 PCB 电源、晶振、引脚复用、传感器安装方向、执行器输出和电磁兼容性。硬件仍然必须按第 8、11 节逐步验证。

### 1.1 适用的硬件范围

本教程主要针对 PX4 的 NuttX/Pixhawk 类飞控，主控通常是 STM32F4、STM32F7、STM32H7 或其他 PX4/NuttX 已支持的 MCU。

如果自制板使用：

- 已有 PX4/NuttX 支持的 MCU 系列；
- 与某个官方板相近的电源、时钟、USB、调试口和传感器连接；
- 基本兼容的 bootloader 启动流程；

那么通常可以复制相近官方板进行移植。

如果 MCU、Flash/RAM 布局、启动方式完全不在 PX4/NuttX 支持范围内，需要先完成 NuttX 芯片级移植，这不是简单复制板卡目录能解决的。

## 2. 当前源码状态与不要重新下载的确认方法


当前目录已经是 PX4 `v1.16.2` 的完整工作树，位于分支 `codex/px4-1.16.2-custom`。不要为了“重新开始”而删除整个目录；这会浪费下载时间，也会丢失你之后写的板卡代码。

打开 PowerShell，进入源码目录：

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'
git status --short --branch
git describe --tags --exact-match
git submodule status --recursive
```

期望看到：

```text
## codex/px4-1.16.2-custom
v1.16.2
```

子模块输出中，正常情况下每一行以空格或 `+` 开头；如果以 `-` 开头，说明该子模块尚未初始化，需要执行：

```powershell
git submodule update --init --recursive --jobs 4
```

### 2.1 如果当前不是 v1.16.2

先确认没有未提交的修改：

```powershell
git status --short
```

有修改时不要执行 `git reset --hard`、`git clean -fd` 或删除目录。先把修改提交到自己的分支，或者另建备份分支。

没有修改时，可以从标签建立开发分支：

```powershell
git switch -c codex/px4-custom-v1 v1.16.2
git submodule update --init --recursive --jobs 4
```

### 2.2 为什么不要直接在标签上开发

`v1.16.2` 是一个固定标签。直接在标签对应的 detached HEAD 状态下修改，后续切换版本时容易丢失提交。应始终在自己的分支上修改，例如：

```text
codex/px4-1.16.2-custom
codex/px4-custom-board
codex/px4-custom-v1
```

### 2.3 建议的源码检查命令

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'

# 当前提交
git rev-parse HEAD

# 与 v1.16.2 的差异
git diff --stat v1.16.2

# 尚未提交的差异
git diff
git diff --cached

# 当前分支
git branch --show-current
```

本目录还提供了一个只读检查脚本：

```powershell
powershell -ExecutionPolicy Bypass -File `
  'C:\Users\Administrator\Desktop\27plane\px4\.codex\scripts\check-cloud-build-setup.ps1'
```

## 3. 配置 GitHub Actions 云编译

> GitHub Actions 每次只构建已经推送到远程仓库的 commit。Windows 中没有提交或没有推送的修改不会进入云端构建。你也可以在 GitHub 网页直接编辑文件，但正式板卡代码仍建议在本地完成差异检查、提交和记录。

### 3.1 先准备自己的 GitHub 仓库

当前本地仓库的 `origin` 指向官方 PX4：

```text
https://github.com/PX4/PX4-Autopilot.git
```

不要尝试把自制代码直接推送到官方仓库。你可以：

- Fork 官方仓库后推送到自己的 fork；或
- 在 GitHub 新建一个私有或公开仓库，把当前源码和提交推过去。

推荐保留 `origin` 为官方 PX4，再添加自己的远程仓库：

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'
git remote -v
git remote add myrepo https://github.com/<你的用户名>/<你的仓库名>.git
```

如果已经存在同名远程仓库，先查看：

```powershell
git remote -v
```

不要重复添加同名 remote。

### 3.2 复制工作流模板

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'

New-Item -ItemType Directory -Force .github\workflows | Out-Null
Copy-Item `
  .codex\github-actions\px4-custom-board.yml `
  .github\workflows\px4-custom-board.yml
```

接下来编辑：

```text
C:\Users\Administrator\Desktop\27plane\px4\.github\workflows\px4-custom-board.yml
```

工作流默认先使用：

```yaml
PX4_BOARD_TARGET: px4_fmu-v6x_default
PX4_BUILD_BOOTLOADER: "false"
```

这是为了先验证 GitHub Actions、子模块、Docker 镜像和制品上传是否正常。第一次运行成功后，再改成自己的目标：

```yaml
PX4_BOARD_TARGET: acme_mypilot-v1_default
PX4_BOOTLOADER_TARGET: acme_mypilot-v1_bootloader
```

如果 donor board 使用树内 bootloader，并把 `PX4_BUILD_BOOTLOADER` 改成 `"true"`，工作流会额外编译 bootloader。`px4io/px4-dev-nuttx-focal:2022-08-12` 与 PX4 1.16.2 仓库内官方 CI 为 NuttX 目标选择的容器一致。

### 3.3 提交并推送

检查即将提交的文件：

```powershell
git status --short
git diff -- .github/workflows/px4-custom-board.yml
git diff -- boards/acme/mypilot-v1
```

示例提交：

```powershell
git add boards/acme/mypilot-v1 .github/workflows/px4-custom-board.yml
git commit -m "Add custom PX4 board support and cloud build"
git push -u myrepo codex/px4-1.16.2-custom
```

也可以把本教程目录纳入版本管理：

```powershell
git add .codex
git commit -m "Document custom PX4 board workflow"
```

如果只想在本地保留教程，不推送 `.codex` 也可以。

### 3.4 在 GitHub 查看构建

推送后：

1. 打开自己的 GitHub 仓库；
2. 进入 `Actions`；
3. 选择 `Build custom PX4 firmware`；
4. 打开最新运行；
5. 查看 `Build PX4 firmware in official NuttX container` 日志；
6. 运行成功后，在该次运行页面底部下载 `px4-custom-<target>-<run_number>` artifact。

工作流会：

- 递归检出 PX4 和子模块；
- 使用 `px4io/px4-dev-nuttx-focal:2022-08-12`；
- 设置 Git safe.directory；
- 执行 `make "$PX4_BOARD_TARGET"`；
- 可选执行 bootloader 目标；
- 生成构建信息；
- 上传 `.px4`、`.elf`、`.bin`、`.hex`、`.map` 和构建信息。

### 3.5 手动触发构建

工作流包含 `workflow_dispatch`。在 GitHub Actions 页面点击 `Run workflow` 即可手动触发。它使用的是 YAML 中当前写死的 `PX4_BOARD_TARGET`。

如果要同时维护多个配置，建议复制成多个明确命名的工作流文件，例如：

```text
px4-mypilot-v1.yml
px4-mypilot-v2.yml
```

不要让同一工作流同时上传同名 artifact。`actions/upload-artifact@v4` 在同一工作流运行中不允许重复 artifact 名称。

### 3.6 私有仓库成本与权限

- 公开仓库通常不需要为 GitHub Actions 分钟数付费，但仍受 GitHub 服务条款、存储和并发限制约束。
- 私有仓库的 Actions 分钟数、存储和并发由账户套餐决定。
- 不要频繁在每次无关改动上触发完整 PX4 构建；可根据需要把 `on.push` 限制到指定分支或路径。
- 容器镜像中的工具版本是固定的，适合复现；升级镜像后要重新做完整构建和硬件回归。

## 4. 选择 donor board 并创建自定义板目录


### 4.1 PX4 板卡目录规则

PX4 会自动发现：

```text
boards/<vendor>/<model>/*.px4board
```

例如：

```text
boards/px4/fmu-v6x/
```

对应的构建目标：

```text
px4_fmu-v6x_default
px4_fmu-v6x_bootloader
```

目标命名规则是：

```text
<VENDOR>_<MODEL>_<LABEL>
```

其中：

- `vendor` 是 `boards` 下的厂商目录名；
- `model` 是具体板型目录名；
- `label` 是 `.px4board` 文件名去掉扩展名；
- `default` 在部分 PX4 命令中可以省略；云工作流为了明确无歧义，始终建议写完整的 `_default`。

### 4.2 如何选 donor board

优先找与你的硬件最接近的官方板，匹配顺序建议如下：

1. 同一 MCU 型号或至少同一芯片系列；
2. 相同 Flash/RAM 容量和封装；
3. 相同 bootloader 方案；
4. 相似的外部晶振、USB、调试口和电源时序；
5. 相似的传感器总线连接；
6. 相似的 PWM、CAN、UART、I2C、SPI 资源。

对 STM32H7 自制板，`boards/px4/fmu-v6x/` 是一个常用参考，因为它包含完整的 NuttX、bootloader、链接脚本、传感器初始化、USB、SDIO、CAN、SPI/I2C 配置。

但不要因为“都是 H7”就盲目复制。不同 H7 型号的 Flash 分区、启动地址、时钟树和引脚定义可能不同。

### 4.3 用 PowerShell 创建目录

下面以示例名称为例：

```text
vendor: acme
model:  mypilot-v1
donor:  boards/px4/fmu-v6x
```

执行前先确认目标目录不存在：

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'

$Vendor = 'acme'
$Model  = 'mypilot-v1'
$DonorVendor = 'px4'
$DonorModel  = 'fmu-v6x'

$Destination = "boards\$Vendor\$Model"

if (Test-Path $Destination) {
    throw "目标目录已存在，停止操作：$Destination"
}

New-Item -ItemType Directory -Path "boards\$Vendor" -Force | Out-Null
New-Item -ItemType Directory -Path $Destination -Force | Out-Null
Copy-Item -Path "boards\$DonorVendor\$DonorModel\*" `
  -Destination $Destination -Recurse

Get-ChildItem $Destination -Force
```

创建后，板卡目标默认形如：

```text
acme_mypilot-v1_default
acme_mypilot-v1_bootloader
```

### 4.4 用 Git 查看复制结果

```powershell
git status --short
Get-ChildItem boards\acme\mypilot-v1 -Recurse -Filter *.px4board
```

不要使用命令行一次性删除 donor 目录或原来的 `boards\px4\fmu-v6x`。自制板的文件应复制到自己的目录，官方板目录保持原样，方便后续对比和升级。

## 5. 修改板卡配置、引脚、总线、驱动与启动脚本


复制完成后，板卡目录中的每一项都要根据硬件原理图核对。以下是常见文件及其用途。

### 5.1 `firmware.prototype`

示例参考：

```text
boards\acme\mypilot-v1\firmware.prototype
```

典型内容：

```json
{
    "board_id": 53,
    "magic": "PX4FWv1",
    "description": "Firmware for the PX4FMUv6X board",
    "image": "",
    "build_time": 0,
    "summary": "PX4FMUv6X",
    "version": "0.1",
    "image_size": 0,
    "image_maxsize": 1966080,
    "git_identity": "",
    "board_revision": 0
}
```

注意：

- `board_id` 必须换成自制板的值；
- `description`、`summary` 改成自己的标识；
- `image_maxsize` 必须与应用程序 Flash 区域一致；
- 不要直接把官方板的 `description` 留在正式固件里。

### 5.2 `default.px4board`

这是 PX4 应用程序的 Kconfig 板级配置，决定：

- 启用哪些驱动；
- 启用哪些飞行模块；
- 串口映射；
- 是否启用网络、UAVCAN、SD 卡等；
- 使用哪个 MAVLink dialect；
- 哪些系统命令和调试工具进入固件。

常见项：

```text
CONFIG_BOARD_TOOLCHAIN="arm-none-eabi"
CONFIG_BOARD_ARCHITECTURE="cortex-m7"
CONFIG_BOARD_SERIAL_GPS1="/dev/ttyS0"
CONFIG_DRIVERS_IMU_BOSCH_BMI088=y
CONFIG_DRIVERS_PWM_OUT=y
CONFIG_MODULES_MAVLINK=y
```

原则：

- 只保留硬件实际存在或确实需要的驱动；
- 先把基础飞行和调试功能编进去，不要一开始就追求最小固件；
- 修改后执行 `git diff`，确认没有误改无关项；
- 配置项拼写错误可能被构建系统静默忽略，因此要查看 Actions 中的 `make` 日志和最终固件大小。

### 5.3 `bootloader.px4board`

它决定 bootloader 构建时的基础配置。它通常比应用程序配置短，但仍必须匹配：

- MCU 架构；
- ROMFS 设置；
- 工具链；
- bootloader 对应的 NuttX 配置。

不是所有板卡都使用 PX4 树内的 bootloader。PX4 1.16.2 中许多 STM32H7 板卡在 `nuttx-config/bootloader/` 下有 bootloader 配置；较早的 F4/F7 平台可能使用单独的 PX4 Bootloader 仓库。修改前先查看 donor 板的结构。

### 5.4 NuttX 配置

重点检查：

```text
nuttx-config/nsh/defconfig
nuttx-config/bootloader/defconfig
nuttx-config/include/board.h
nuttx-config/include/board_dma_map.h
nuttx-config/scripts/script.ld
nuttx-config/scripts/bootloader_script.ld
```

分别对应：

- 应用程序的 NuttX 外设和驱动；
- bootloader 的 NuttX 配置；
- MCU 引脚、时钟和复用；
- DMA 通道限制；
- 应用程序 Flash/RAM 布局；
- bootloader Flash 布局。

本教程不执行本地 `boardconfig` 或 `menuconfig`。直接以 donor board 的 `.px4board` 文件和 NuttX `defconfig` 为基准，对照原理图修改配置；提交后在 GitHub Actions 中验证 Kconfig、依赖和编译结果。

修改后立刻查看差异：

```powershell
git diff -- boards/acme/mypilot-v1
```

不要在不了解后果的情况下使用“全部恢复默认”或批量删除配置文件。

### 5.5 `src/` 目录

常见文件和职责：

| 文件 | 重点 |
| --- | --- |
| `board_config.h` | PX4 板级宏、传感器中断、电源、LED、版本信息 |
| `hw_config.h` | 外设和硬件版本定义 |
| `init.cpp` | 板级初始化、总线、传感器供电和 GPIO |
| `spi.cpp` | SPI 总线、片选和总线时钟 |
| `i2c.cpp` | I2C 总线实例和引脚复用 |
| `timer_config.cpp` | 定时器、PWM、ICU 和 DMA 映射 |
| `usb.c` | USB 引脚、检测、VBUS 和串口 |
| `sdio.c` | SD 卡接口 |
| `can.c` | CAN 控制器和引脚 |
| `led.c` | LED 极性、颜色和状态 |
| `mtd.cpp` | Flash/参数存储分区 |

其中最容易出问题的是：

- 引脚编号写错；
- SPI 片选或总线号错；
- I2C 地址冲突；
- 定时器通道与 PWM 输出不一致；
- DMA 通道复用冲突；
- USB VBUS 检测极性反了；
- Flash 起始地址和链接脚本不一致。

### 5.6 `init/` 目录

常见文件：

```text
init/rc.board_defaults
init/rc.board_sensors
```

`rc.board_defaults` 用于设置板级默认参数和设备启动，例如：

- 电源监控默认参数；
- 网络/UAVCAN 配置；
- 安全开关启动；
- GPIO 扩展器；
- 板卡硬件版本判断。

`rc.board_sensors` 用于启动板载传感器，例如：

- IMU 的总线号和片选；
- 磁力计和气压计地址；
- 外部传感器供电；
- 电源监控芯片。

启动脚本里的参数必须与原理图、驱动和 `default.px4board` 配套。不要只因为固件能编译就认为驱动能在真实硬件上工作。

## 6. 分配 board ID 并核对 Flash 布局


### 6.1 为什么 board ID 很重要

PX4 的 `.px4` 固件包中包含 `board_id`。上传工具会读取 bootloader 报告的板卡类型，并与固件包中的 `board_id` 比较。两者不匹配时，通常会拒绝烧录。

因此必须保证：

1. bootloader 的 board ID 正确；
2. 应用程序固件的 board ID 正确；
3. 两者一致；
4. 不与无关硬件共用官方 ID；
5. ID 一旦发布，不再随意改变。

### 6.2 查看仓库中已使用的 ID

在源码根目录运行 PowerShell：

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'

$rows = Get-ChildItem boards -Recurse -Filter firmware.prototype |
    ForEach-Object {
        try {
            $json = Get-Content $_.FullName -Raw | ConvertFrom-Json
            [PSCustomObject]@{
                BoardId = [int]$json.board_id
                File    = $_.FullName.Substring((Get-Location).Path.Length + 1)
            }
        }
        catch {
            Write-Warning "无法解析：$($_.FullName)"
        }
    }

$rows | Sort-Object BoardId, File | Format-Table -AutoSize
```

这只是检查当前源码树中能看到的 ID。它不等于全球分配登记表。正式产品或准备提交上游时，还应通过 PX4 官方开发渠道确认 ID，避免与他人冲突。

### 6.3 修改 board ID

在 `firmware.prototype` 中修改：

```json
"board_id": 6000
```

> `6000` 只是示例占位值，**不要不检查就直接使用**。先按上一节查重，并确认 bootloader 使用同一个值。

同时更新：

```json
"description": "Firmware for the ACME MyPilot v1 board",
"summary": "ACME_MyPilot_v1",
"version": "0.1"
```

如果使用了独立的 PX4 Bootloader 仓库，还要修改它对应板卡目标中的 board ID。只有两边一致，QGC 和 `px_uploader.py` 才会把它识别为同一板卡。

### 6.4 核对应用程序 Flash 区域

以 FMUv6X 参考板为例：

- bootloader 链接脚本使用 `0x08000000` 开始的 128 KiB；
- 应用程序链接脚本使用 `0x08020000` 开始的 1920 KiB；
- `firmware.prototype` 的 `image_maxsize` 为 `1966080` 字节，即 1920 KiB。

这三个值必须相互一致：

```text
bootloader 占用区域
    + 应用程序区域
    + 参数/其他保留区域
    <= MCU 可用 Flash
```

如果自制板换成不同 Flash 容量、不同分区或不同 MCU，不能直接照搬示例数字。必须先确认芯片手册、链接脚本和 bootloader 的分区定义。

### 6.5 检查链接脚本

```powershell
Get-Content boards\acme\mypilot-v1\nuttx-config\scripts\script.ld |
  Select-String -Pattern 'MEMORY|ORIGIN|LENGTH|FLASH'

Get-Content boards\acme\mypilot-v1\nuttx-config\scripts\bootloader_script.ld |
  Select-String -Pattern 'MEMORY|ORIGIN|LENGTH|flash'
```

至少确认：

- 应用程序 `FLASH ORIGIN` 位于 bootloader 之后；
- 应用程序 `LENGTH` 不超过预留空间；
- bootloader 区域没有被应用程序覆盖；
- 参数区、SD 卡、外部 Flash 等配置没有与链接脚本冲突。

## 8. 烧录与首板调试


### 8.1 应用程序固件：用 Windows QGroundControl

把 GitHub Actions artifact 中的 `.px4` 文件下载到 Windows，再交给 QGroundControl 烧录。

解压 artifact 后，文件路径通常类似：

```text
<解压目录>\build\acme_mypilot-v1_default\acme_mypilot-v1_default.px4
```

操作步骤：

1. 断开飞控 USB。
2. 打开 Windows QGroundControl。
3. 进入 `Vehicle Setup -> Firmware`。
4. 插上飞控 USB。
5. 选择 PX4 Flight Stack。
6. 勾选 `Advanced settings`，选择 `Custom firmware file`。
7. 选择刚才生成的 `.px4` 文件。
8. 开始烧录并等待校验完成。

注意：首次烧录自制 bootloader 不是这个流程。QGC 的这个功能用于已经能进入 bootloader 的板卡。

### 8.2 bootloader：使用 SWD/JTAG 或芯片 DFU

第一次把 bootloader 写入空白 MCU 或替换 bootloader 时，通常需要：

- ST-LINK、J-Link、Black Magic Probe 或板载调试器；
- SWD/JTAG 接口；
- STM32CubeProgrammer、OpenOCD、J-Link 工具或其他芯片厂商工具；
- 正确连接 BOOT0、复位、电源和地；
- 确认 bootloader 链接地址和选项字节。

以 FMUv6X 类 H7 参考设计为例，bootloader 链接在 `0x08000000`，应用程序从 bootloader 之后的区域启动。但自制板必须按自己的 MCU、Flash 分区和 bootloader 链接脚本核对，不能只照抄地址。

烧录 bootloader 后：

1. 断电再上电；
2. 连接 USB；
3. 确认电脑能识别 PX4 bootloader；
4. 用 QGC 自定义固件烧录应用程序；
5. 如果 QGC 报 board ID 不匹配，先停下检查，不要反复强制刷写。

### 8.3 首板调试顺序

建议按以下顺序推进：

1. 只用限流电源给板子供电，先不接电机、电调、GPS 和外部负载；
2. 测量 3.3 V、5 V、传感器电源和 MCU 电源轨；
3. 检查复位、BOOT0、晶振、SWD 和 USB；
4. 通过 SWD 确认 MCU 能被识别；
5. 烧录 bootloader，确认 USB 枚举；
6. 烧录应用程序，查看启动日志；
7. 检查 `dmesg`、`ver all`、温湿度/气压/IMU 状态；
8. 校准加速度计和磁力计，核对所有传感器轴向；
9. 接电调但不接螺旋桨，测试 PWM/DShot 输出和电机顺序；
10. 检查电源监控、GPS、RC、CAN 和日志存储；
11. 完成台架测试后，才考虑安装螺旋桨和试飞。

### 8.4 QGC MAVLink Console 常用检查

进入 QGC 的 MAVLink Console，可运行：

```text
ver all
dmesg
param show
sensors status
listener sensor_accel
listener sensor_gyro
listener battery_status
```

不同板卡和配置可用的命令可能不同；以实际固件中的模块为准。

## 9. 版本管理和后续升级


### 9.1 保持自定义代码集中

建议把自制板相关修改尽量集中在：

```text
boards/<vendor>/<model>/
```

必要时再修改：

```text
src/drivers/
src/modules/
platforms/nuttx/
```

自定义越集中，升级到 PX4 1.17、1.18 等新版本时越容易。

### 9.2 升级 PX4 的典型流程

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'

git status --short
git fetch origin --tags

# 查看目标新版本
git tag --list 'v1.1*' --sort=-version:refname | Select-Object -First 20
```

在新分支上工作，例如：

```powershell
git switch -c codex/px4-update-test v1.16.3
```

然后把自制板目录和必要修改带过去。可以：

- 复制整个 `boards/<vendor>/<model>/`；
- cherry-pick 自定义板提交；
- 生成并应用补丁；
- 对比新版官方 driver、NuttX 配置和启动脚本的变化。

不要直接合并一个全新的 PX4 分支后假设硬件仍然兼容。升级后必须重新编译、检查配置差异并做台架测试。

### 9.3 可复现构建原则

- 固定 PX4 版本或 commit；
- 固定 Docker 镜像 tag；
- 记录构建目标；
- 记录固件的 SHA-256；
- 保留每次硬件测试结果；
- 不依赖“某个同事电脑上的未提交修改”。

## 10. 故障排查

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| `Actions` 页面没有显示工作流 | 文件不在 `.github/workflows/`、YAML 无效或分支未推送 | 检查路径、提交和默认分支；查看仓库 Actions 设置 |
| `PX4 build target not found` | 目录层级、vendor/model 名称或 label 写错 | 检查 `boards/<vendor>/<model>/<label>.px4board`，工作流必须使用完整目标名 |
| 子模块检出失败 | 私有子模块权限、网络或 checkout 配置错误 | 检查 Actions 日志；确认 checkout 使用 `submodules: recursive` |
| Docker 镜像拉取失败 | 镜像 tag 错误、Docker Hub 限流或网络故障 | 确认使用 `px4io/px4-dev-nuttx-focal:2022-08-12`，重试或稍后重新运行 |
| 配置项改了但功能没出现 | Kconfig 符号拼写错误、依赖未启用、配置文件不是当前目标 | 检查云构建日志和生成的 NuttX `.config`；核对 `default.px4board` |
| 驱动能编译但硬件不工作 | 总线号、片选、地址、供电或中断错误 | 对照原理图检查 `spi.cpp`、`i2c.cpp`、`init.cpp` 和 NuttX 配置 |
| QGC 提示 board ID 不匹配 | bootloader 和应用程序 ID 不同，或用了官方固件 | 修改 `firmware.prototype` 和 bootloader 对应 ID，确认两边一致 |
| 固件过大 | 驱动、模块、日志或网络功能过多，Flash 分区过小 | 精简配置；确认 `image_maxsize` 和链接脚本，不要无依据扩容 |
| Actions 没有 artifact | 构建失败，或上传路径没有匹配文件 | 查看 `if-no-files-found: error` 对应的失败步骤和构建目录 |
| 首次烧录后不启动 | bootloader 地址、Flash 分区、时钟、复位或电源错误 | 用 SWD 读取芯片状态，核对链接脚本和板级初始化，不要继续盲刷 |
| 私有仓库 Actions 突然不可用 | 账户额度或计费限制 | 检查 GitHub Billing/Actions 设置 |

### 10.1 子模块问题

在 PowerShell 中检查并修复子模块：

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'
git submodule sync --recursive
git submodule update --init --recursive --jobs 4
git submodule status --recursive |
  Select-String -Pattern '^-'
```

### 10.2 快速确认当前目标文件

```powershell
Set-Location 'C:\Users\Administrator\Desktop\27plane\px4'

Get-ChildItem boards\acme\mypilot-v1 -Filter *.px4board |
  Select-Object -ExpandProperty Name
```

工作流中的完整目标名应由目录和文件名组成，例如：

```text
boards/acme/mypilot-v1/default.px4board
```

对应：

```text
acme_mypilot-v1_default
```

### 10.3 云构建失败时先看什么

按顺序检查：

1. Actions 是否检出了正确的 commit；
2. 子模块是否完整；
3. `PX4_BOARD_TARGET` 是否与仓库中的 `.px4board` 完全一致；
4. 失败发生在目标校验、Docker 启动、CMake 配置还是 C++ 编译；
5. 日志中第一个 `error:` 之前的上下文；
6. 是否把本地未提交的修改误认为已经推送。

不要只在 GitHub Actions 页面反复点击重跑；先修复日志中的第一个真实错误。

## 11. 上电与试飞检查表


### 11.1 PCB 和电源

- [ ] 原理图和 PCB 已核对 MCU 型号、封装和引脚；
- [ ] Flash/RAM 容量与链接脚本一致；
- [ ] 3.3 V、5 V、传感器电源和参考电压已测量；
- [ ] 上电顺序和复位时序符合芯片要求；
- [ ] USB、SWD、BOOT0、晶振和调试口已核对；
- [ ] 电源反接、过压、欠压和浪涌保护已检查；
- [ ] 首次上电使用限流电源；
- [ ] 电机和电调首次测试时拆除螺旋桨。

### 11.2 bootloader 和固件

- [ ] bootloader 与应用程序 board ID 一致；
- [ ] bootloader 和应用程序链接地址不重叠；
- [ ] `image_maxsize` 与 Flash 分区一致；
- [ ] QGC 可以进入 bootloader 并完成校验；
- [ ] 启动日志中无持续 hardfault、watchdog 或内存错误；
- [ ] 参数可保存并在重启后保留；
- [ ] USB、SD 卡、串口和日志功能已验证。

### 11.3 传感器和执行器

- [ ] IMU 安装方向与板卡坐标系一致；
- [ ] 加速度计、陀螺仪和磁力计校准通过；
- [ ] 气压计和温度传感器读数合理；
- [ ] RC 输入和失控保护已验证；
- [ ] PWM/DShot 输出频率和通道映射正确；
- [ ] 电机顺序和转向正确；
- [ ] 电调信号在通电和复位时不会误动作；
- [ ] GPS、CAN、UAVCAN、外部 I2C 设备按需验证。

### 11.4 飞行前

- [ ] 已完成台架振动和温升测试；
- [ ] 日志可以正常记录并下载；
- [ ] 电池电压和电流监测准确；
- [ ] failsafe、return、land 和 emergency 行为已配置；
- [ ] 试飞区域安全，人员远离；
- [ ] 有紧急断电手段；
- [ ] 首飞使用低风险模式并逐步扩大包线。

## 13. 最终交付顺序

推荐按下面的顺序执行，不要跳步：

```text
1. 确认真实源码位于 v1.16.2，35 个子模块完整
2. 在 GitHub 建立自己的仓库并添加工作流
3. 先用 px4_fmu-v6x_default 在 Actions 做烟雾测试
4. 选择最接近的 donor board
5. 复制到 boards/<vendor>/<model>
6. 修改 board ID、Flash 布局、引脚、总线、驱动和启动脚本
7. 把工作流目标改成自定义应用程序目标并云编译
8. 需要时打开 PX4_BUILD_BOOTLOADER 云编译 bootloader
9. 首次 bootloader 用 SWD/JTAG 或芯片 DFU 烧录
10. 下载应用程序 .px4，用 Windows QGC 烧录
11. 完成限流、电源、传感器、执行器和台架测试
12. 为验证过的源码和固件打标签并保存 artifact 记录
```

完成以上步骤后，你得到的是一条不依赖本地编译环境、可追溯且可重复的 PX4 自制飞控云编译流程。
